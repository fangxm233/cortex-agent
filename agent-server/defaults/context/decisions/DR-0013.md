# DR-0013: Run / Session / Engine Run Model

**Date:** 2026-09-12
**Author:** Cortex
**Status:** Accepted

## Context

The running-agent refactor (`/root/.cortex/plan/running-agent-refactor.md`, branch `refactor/runs`) collapsed the
path from a platform message to a backend process into three nouns — **run**, **session**,
**engine** — and one event stream. A run is one execution of one user request; a session owns the
engine it resumes into; the engine is the backend process. This record fixes the ten decisions
that define that model and names, for each, the surface it replaces. Those legacy surfaces are
retired incrementally on the branch; where one is still present it is transitional, not a
reintroduction.

## Decisions

| # | Decision | Replaces |
|---|---|---|
| D1 | A run is the ownership object, and the background-continuation phase stays open on the same run's event stream until pending background work reaches zero or the engine dies. | The `ContinuationSink` callback contract, `pushTurnEvent`, and the synthetic `spontaneous` turn as things the orchestrator wires by hand. |
| D2 | Steer is a run method; delivery is an event (`injection_delivered` / `injection_rejected`). | `InjectionAckSink` and the duck-typed `agentProcess` injection path. |
| D3 | One `RunRequest`; a backend-neutral `EngineSpec` carries backend-private options in a discriminated union. | `RunAgentOptions` (with its `[key: string]: any`) and the flat backend-passthrough fields of `AgentSpawnConfig`. |
| D4 | A session owns the engine it resumes into; `SessionEngines` is the only pool owner. | The Claude module-level session map, PI's instance map, and the `closeSession*` re-exports from the adapter barrel. |
| D5 | Config is resolved once per run, five layers deep; `mode.json` becomes `data/agent-state.json`; `!backend` / `!model` become channel-scoped overrides. | Global backend/model/mode read as run inputs, and the `backend:channel` key in `sessions.json`. |
| D6 | Prompt assembly is two functions: `composeSystemPrompt` and `composeUserPrompt`. | The three-way split across `spawn-config.rulesPrompt`, `buildConversationPrompt`, and `buildStepPrompt`. |
| D7 | Rate-limit handling, fallback, and resume are run policy; notifications are events. | The facade's own fallback loop, the `recordResume` calls scattered across surfaces, and the per-surface copies of the rate-limit hold. |
| D8 | `startRun` opens the execution record; `RunRegistry` is the one index of live runs and background holds. | `core/running-executions.ts`, `core/bg-held-sessions.ts`, and the per-call-site execution/registry boilerplate. |
| D9 | Capabilities are declared per `EngineSession` and checked by the run; Claude TUI retires to print with a warning. | The optional, duck-typed `AgentProcess` methods and `claudeBackend: 'tui'` as a live mode. |
| D10 | `agent-adapter/` depends only on `core` (plus event types); host collaborators are injected. | Adapter runtime imports of `domain/costs` (throttle and usage store), `domain/mcp`, and `domain/agents/subagent`. |
