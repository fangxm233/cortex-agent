| `conduit-queue.ts` | singleton | per-conduit serial Promise queue (conduitQueues Map + enqueue(), [S6-B]) |
| `delta-coalescer.ts` | streaming | Token-level assistant streaming. `createDeltaCoalescer` batches incremental chunks per `blockId` — one publish per `CORTEX_STREAM_DELTA_MS` window (default 120) or per 400 accumulated chars, `seq` counting from 0 per block — so the bus, the SSE queues and the browser see a bounded event rate however chatty a backend is. `createSessionDeltaStream` binds it to a session and is the SINGLE gate on who streams at all: a `web:` channel with a session id, unless `CORTEX_STREAM_DELTAS=0`. It returns null for Slack / Feishu / Ink-TUI / thread channels, which is what keeps partial text out of OutputStream |
| `mid-turn-inject.ts` | orchestration | **The inject-vs-queue branch of `AgentRunner.route`.** A plain user message arriving while its channel already has a live turn is written straight into that turn's backend stdin instead of waiting behind it in `conduit-queue` (Claude print mode only — `Capability.MidTurnInject`). Pure gates `isInjectableMessage` (a `!command` carries its own execution semantics; a synthetic wake/callback must open its OWN turn; empty text) + `backendSupportsInject`; `tryInjectIntoLiveTurn` returns false on every declined path so today's queue behaviour is preserved byte-for-byte. Two measured behaviours shape it: (1) **landing is a race** — on a tool-result boundary the message folds into the running turn (ONE result, already-awaited promise covers it), mid-text-generation the CLI consumes it only AFTER that turn's result and starts a turn of its own, so the `ContinuationSink` registered here streams that spontaneous reply (assistant text → the streaming callback captured at inject time + history + `session.message`, tool calls likewise, `session.status` re-marked running then sealed) instead of dropping it; (2) **writing ≠ delivering** — a stdin write only QUEUES the message inside the CLI (measured: written at 6.0s, read at 12.0s), and the `--replay-user-messages` echo fires exactly at consumption. So the message enters the record in a **two-phase commit**: at write time only the `session.message` is published, carrying `pending: true` — nothing is appended, because until the model has read it everything the agent is emitting was produced WITHOUT it and belongs above it; at the echo the history record and the ledger turn are written together, both stamped with the consumption time, and `session.message.delivered` is published last (a client refetching on that event must find the record) carrying `messageTs` (the pending row's key) + `committedTs` (the history/order key it is re-keyed to, which is what a refetch returns, so the live and fetched rows dedupe as one). The ledger turn moves WITH the history record because rewind resolves turn indices positionally over the history's user records — a record without its turn shifts every later edit index. A message never consumed (wedged CLI, process death, the injection window closing) is committed at that seal instead, so a message the user really sent is never silently lost; `commit` is single-fire, so an echo followed by a result records it once. Holds a single-fire busy bracket with a leak cap (`CORTEX_INJECT_WAIT_MAX_S`, default 600s) so a deferred daemon restart cannot kill the backend mid-reply. All side effects injected (`MidTurnInjectDeps`); production wiring in `agent-runner.buildInjectDeps` |

| `agent-runner.ts` | orchestration | Plain user-message path: session/status/ledger/callbacks + runConversation (no thread), message-router.ts default branch sole execution path ([S8]). `route()` first tries **mid-turn injection** (`_tryInject`, injectable; production `_tryInjectReal` + `buildInjectDeps` wire `mid-turn-inject.ts` to the same history/bus/busy-gate seams `_executeReal` uses, so an injected message lands in the transcript identically to a queued one) — cheapest gates first, since route() is the hot path for every inbound message; on success it returns BEFORE the queue machinery (no markQueued, no enqueue, no `track` — the injection path owns its own bracket), otherwise the conduit-queue path is unchanged. At the conversation-history append sites (appendUser / appendAssistant / appendTool) also publishes `session.message` via `publishSessionMessage` (S4 chat live stream). Its onProgress wrapper calls `emitTurnProgress` (exported, unit-tested) → updates the running execution's live `numTurns` (`runningExecutions.setNumTurns`) + publishes `session.turn`, so the Web composer shows the REAL agent-turn count live (not user-message rounds). For web sessions it also opens a `createSessionDeltaStream` for the turn: `onAssistantDelta` feeds it, `onAssistantMessage` flushes that block before publishing the authoritative `session.message` (which now carries the same `blockId`), and the `finally` disposes it so no preview outlives the turn |

| `session-events.ts` | S4 chat | `publishSessionMessage(payload)` — emit a `session.message` CortexEvent on the shared bus (read from job-registry `ctx.bus`, the same seam thread-callback uses); no-op when no bus is wired. The payload's optional `pending` flag marks a user message written into a live turn's backend that the model has not read yet — surfaced but not yet in history. Also `publishSessionMessageDelivered` (the mid-turn injection COMMIT: the pending message has now been consumed by the model, or its injection window closed — `messageTs` keys the pending row, `committedTs` is the history ts the client re-keys it to), `publishSessionStatus` (running true/false per turn), `publishSessionTurn` (live agent `numTurns` per turn_progress — the composer's real turn count) and `publishSessionRewound` (message edit + rewind: the transcript changed shape — live clients drop buffered tails + refetch). `publishSessionMessageDelta` emits the token-level `session.message.delta` preview (blockId + increment + seq), published only through the delta-coalescer for web sessions and never persisted; the `session.message` carrying the same `blockId` supersedes it |

| `web-bg-hold.ts` | helper | The WEB analogue of lifecycle.ts's Slack status-message bg-hold — closes the gap where a `web:` turn ending with a live background task fell through both hold paths (sink dropped, session sealed idle, continuation untracked). holdWebForBg keeps the session.status stream live (running:true, backgroundRunning:true), registers a ContinuationSink that streams the spontaneous continuation as new session.message events, arms the shared bg-wait-guard (busy bracket + grace + max-wait), and seals running:false on completion / grace / interrupt.
